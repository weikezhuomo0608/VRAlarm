| 发现 | 性质 | 处理 |
| --- | --- | --- |
| 检测循环跑在主线程消息队列上，没有任何唤醒能力 | 结构性，正是“整天没提醒”的根因 | 每轮检测结束后安排一次系统唤醒闹钟（本轮间隔的三倍，下限 90 秒）；循环正常时每轮把它推后，停住时才触发 |
| `apply()` 抛出的异常既没有捕获也没有重新排期 | 会导致整条轮询静默终止，或以未捕获异常结束进程 | 捕获后记入记录并按间隔重试；`busy` 在调用前就已复位，不会卡死 |
| 被互斥跳过的场次没有被标记为已提醒 | 与界面“不会叠着响”的承诺不符：第一位响铃一停，下轮就会接着响 | 跳过的场次标记为已处理，只记入记录 |
| 新增主播或改房间号会继承旧编号的场次状态 | 加入时已在播会被当成刚开播而误响；换房间号后旧场次可抑制新提醒 | 改动时重置该主播的场次与上次状态，并把加入时间记为当前 |
| `parse()` 同时比对房间号与主播 UID | 两个接口对同一房间的 UID 可能不同，一旦不一致该主播永久无法提醒 | 只按房间号校验，UID 仅用于跳转 |
| 三处写死的版本号（界面页脚、通知排查包 README、预览状态） | 版本更新后界面仍显示旧号 | 改为从已安装包信息读取 |
| 后台启动失败与“通知被拒”共用同一个提示位 | 启动失败的提示会一直挂在守候页 | 拆成两个字段，服务起来或检测成功即撤下；通知恢复可用时“通知被拒”提示也一并撤下 |
| 测试响铃期间的首次开播被当作重复丢弃 | 真实开播可能被一次 60 秒测试挡住 | 真实开播改为打断测试铃 |
| 填入不存在的房间号提示“B 站接口返回 -400，等待重试” | 文案误导 | 改为“没有找到这个直播间，请检查房间号” |

**仍未验证**：上述九项在真机上的实际表现。保活唤醒能否在用户的手机（小米/澎湃）上按预期触发、看门狗能否在被系统杀掉后成功拉起服务，取决于该机型的自启动与电池策略，应用无法自行验证，也无法突破系统强行停止。

## 真机反馈的适用范围

测试者反馈此前兼容版本在小米可以播放声音，另有 Vivo 正常使用反馈。针对一份 1.0.5 系统报告，确认前台守候服务正在运行，并发现设备管理策略固定拒绝通知；这不能代表所有小米设备的原因或完整兼容性。

原生测试 APK 已完成编译，没有在本项目验证环境的真实手机上执行。浏览器模拟通信也不等于实际 Android 服务、声音或锁屏行为。
