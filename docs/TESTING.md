**第三次真机反馈（2026-09-11）**：从最近任务划掉应用后，守候仍不恢复。

- 这是**系统行为，不是缺陷**：在小米/澎湃等系统上，划掉应用等于系统级强杀——前台服务、已授予的权限、以及恢复用的闹钟会被一起停掉，应用无权否决。已发布的 1.0.5 同样如此，而且它连恢复用的闹钟都没有（全天守候无任何定时唤醒），所以「原版能做到」并不成立。
- 与本次反馈同时成立的一个事实值得记录：1.1.0 已埋了约 90 秒的保活闹钟与 15 分钟看门狗，划掉后仍不恢复，说明恢复用的闹钟很可能根本没有被投递（自启动未生效），或投递了但系统拒绝启动前台服务。
- 本版据此新增两件事：①**中断记录**——检测实际开始时间比服务自行安排的时间晚 5 分钟以上、且当时处于提醒时段内时，写入「守候曾被中断」并附上晚了多久；这是区分上述两种情况的唯一证据。②**指引补全**——守候页的中断提示补上最容易漏掉的一步（最近任务里长按卡片锁定）与「开启无障碍守候辅助」入口，无障碍说明写清它为何是划掉后台后恢复最快的一条路（无障碍服务由系统自行重新绑定）。
- **尚未真机确认**：中断记录能否按预期出现、开启无障碍辅助后划掉后台是否能被系统重新拉起。

**尚未验证**：本版 Android 端 Java 已用 Android SDK 35（platform-35_r02）与 build-tools 35.0.0 完整编译通过，经 D8 转换、zipalign 对齐、apksigner v2/v3 签名校验通过，产物为 `build/ManquAlarm-multi-1.1.0.apk`（独立包名 `dev.hazel.livealarm.multi`，`versionCode=7`、`versionName=1.1.0`，应用名「VR闹钟」，可与原版并存）。**但尚未在真机上运行过**：多主播轮询、互斥响铃、头像下载与缓存、升级迁移、备份恢复、保活唤醒与看门狗均只经过编译与纯 Java 层测试，没有端到端执行。头像识别依赖 B 站 `get_anchor_in_room` 接口的当前返回结构，未在真实网络下验证（识别失败会退化为「主播 <房间号>」并允许手动改名，头像退回首字母）。

真机需重点复核：安装后与旧版并存是否互不干扰（两个应用同时开启守候会各响一次，建议只留一个）、多主播同时开播是否只响一次、识别失败时能否改名保存、缓存头像是否正常显示、加入名单后长时间不打开应用是否仍能按间隔检测。

**首次真机反馈与修复（2026-09-10）**：用户在真机上遇到两件事。

1. 「识别主播信息」报「操作未完成，请重试」。原因是 `Bridge.request` 把动作丢在 UI 线程执行，而该动作在主线程发起网络请求，抛出的 `NetworkOnMainThreadException` 消息为 null，被兜底文案掩盖。已改为在后台线程完成并延迟回包，且兜底文案在消息为空时带上异常类名。**此项已在真机确认修复。**
2. 主播开播没有提醒，事后打开应用才补上响铃；守候页长期显示「网络未连接」，但实际上已联网。查证结果：前者是**全天守候不安排任何定时唤醒**——`TimeRules.nextBoundary` 在 `allDay` 下返回 0，因此进程被系统杀掉后没有任何机制能唤醒它（新建的独立应用也不会继承旧版的“自启动/电池不限制”授权），已新增每 15 分钟的看门狗闹钟尝试自行恢复，并在守候页把心跳中断明确显示出来；后者是本版引入的回归——重写轮询循环时漏了「检测成功即清除 networkError」，已在 `apply()` 中补回，并让网络判断在 Wi-Fi/移动数据切换的瞬间不再误报断网。**这两项尚未在真机确认。**

**第二次全量复查（2026-09-11，1.1.0）**：针对“不要再出现这类问题”做了一次从头到尾的检查，并把发现的问题一并修掉。

| 发现 | 性质 | 处理 |
| --- | --- | --- |
| 检测循环跑在主线程消息队列上，没有任何唤醒能力 | 结构性，正是“整天没提醒”的根因 | 每轮检测结束后安排一次系统唤醒闹钟（本轮间隔的三倍，下限 90 秒）；循环正常时每轮把它推后，停住时才触发 |
| `apply()` 抛出的异常既没有捕获也没有重新排期 | 会导致整条轮询静默终止，或以未捕获异常结束进程 | 捕获后记入记录并按间隔重试；`busy` 在调用前就已复位，不会卡死 |
| 被互斥跳过的场次没有被标记为已提醒 | 与界面“不会叠着响”的承诺不符：第一位响铃一停，下轮就会接着响 | 跳过的场次标记为已处理，只记入记录 |
| 新增主播或改房间号会继承旧编号的场次状态 | 加入时已在播会被当成刚开播而误响；换房间号后旧场次可抑制新提醒 | 改动时重置该主播的场次与上次状态，并把加入时间记为当前 |
| `parse()` 同时比对房间号与主播 UID | 两个接口对同一房间的 UID 可能不同，一旦不一致该主播永久无法提醒 | 只按房间号校验，UID 仅用于跳转 |
| 三处写死的版本号（界面页脚、通知排查包 README、预览状态） | 版本更新后界面仍显示旧号 | 改为从已安装包信息读取 |
| 后台启动失败与“通知被拒”共用同一个提示位 | 启动失败的提示会一直挂在守候页 | 拆成两个字段，服务起来或检测成功即撤下；通知恢复可用时“通知被拒”提示也一并撤下 |
| 测试响铃期间的首次开播被当作重复丢弃 | 真实开播可能被一次 60 秒测试挡住 | 真实开播改为打断测试铃 |
| 填入不存在的房间号提示“B 站接口返回 -400，等待重试” | 文案误导 | 改为“没有找到这个直播间，请检查房间号” |

**仍未验证**：上述九项在真机上的实际表现。保活唤醒能否在用户的手机（小米/澎湃）上按预期触发、看门狗能否在被系统杀掉后成功拉起服务，取决于该机型的自启动与电池策略，应用无法自行验证，也无法突破系统强行停止。
